# INVESTIGATOR_PLAYBOOK.md — Project Sentinel

> **Purpose:** This playbook defines the standard operating procedure for fraud
> investigators working cases generated by Project Sentinel. It covers case intake,
> evidence review, false-positive assessment, OSINT, graph analysis, decision
> recommendation, escalation, and case closure.
>
> **Audience:** Fraud Analysts (Tier 1 and 2), Fraud Operations Lead, Legal.
>
> **Status:** Operational template. All thresholds and SLAs marked

## Investigator Principles

Every investigator working Sentinel cases operates under these principles:

1. **Evidence first.** Every decision is grounded in documented evidence, not intuition.
2. **FP discipline.** When in doubt, the burden of proof lies with the fraud hypothesis, not the contractor.
3. **Proportionality.** Match action severity to evidence strength. Monitoring ≠ restriction.
4. **Auditability.** Document every step. If it isn't written down, it didn't happen.
5. **Contractor protection.** Legitimate contractors are not adversaries. False positives harm real livelihoods.

***

## Case Priority and SLA

Cases are generated in four priority bands. Investigators work highest-priority
cases first within each queue refresh cycle.

| Band | Score | SLA | Description |
|------|-------|-----|-------------|
| **CRITICAL+** | 9–10 or Fatal rule | 4 hours | Immediate review; likely restriction pending |
| **CRITICAL** | 7–9 | 24 hours | Same-day investigation |
| **HIGH** | 5–7 | 48 hours | Next business day |
| **REVIEW** | 3–5 | 5 business days | Secondary check queue |

Queue is capped at 25 CRITICAL/CRITICAL+ cases per run to match
realistic investigator capacity. Cases above the cap are held in overflow
and picked up in the next cycle.

## Step 1 — Case Intake

When a case is assigned, the investigator completes the following intake steps
before reviewing any evidence.

### 1.1 Verify case metadata
- Confirm driver ID, case ID, and case generation timestamp.
- Confirm confidence band and composite score.
- Note which signals fired and their severity tiers.
- Note whether the driver is a ring member (graph flag present).

### 1.2 Check for prior history
- Has this driver been investigated before? What was the outcome?
- Are there prior appeals filed by this driver?
- Is this driver part of any previously closed ring or ongoing investigation?

### 1.3 Confirm evidence integrity
- Verify SHA-256 hash of the case file matches the hash recorded at generation.
- If hash mismatch: do not proceed. Escalate to Fraud Ops Lead immediately.

### 1.4 Document intake
- Log case intake timestamp, investigator ID, and initial confidence assessment.

## Step 2 — Evidence Review

Work through each evidence category in this order. Document findings as you go.

### 2.1 Trip telemetry evidence
- Review GPS signal anomalies: impossible transit, route entropy, geofence misses.
- Check airplane mode events and connectivity gaps.
- Note trip timestamps and compare against claimed delivery times.
- Flag: Are anomalies isolated (single trip) or clustered (pattern across sessions)?

### 2.2 Device evidence
- Review device integrity flags: emulator, rooted device, developer mode.
- Check device identifier history: has this device been seen on other accounts?
- Note OS version and hardware metadata consistency.
- Flag: Does device state indicate capability for automation or GPS spoofing?

### 2.3 Offer and incentive evidence
- Review offer acceptance latency: is it consistently sub-human?
- Check cherry-pick pattern: rapid accept/decline on low-value orders.
- Review incentive claim rate vs peer cohort.
- Flag: Is there a sustained automation pattern or a one-off event?

### 2.4 Payout evidence
- Check for payout account changes relative to settlement dates.
- Review payout instrument sharing with other accounts.
- Note any pre-change login anomalies (failed attempts, new device).
- Flag: Is payout change timing suspicious relative to settlement schedule?

### 2.5 OSINT evidence (see Step 4)
- Note OSINT enrichment outputs (identity verification, device intelligence,
  address type, account resale check, contractor presence).
- Flag any OSINT red flags or unresolvable identifiers.

## Step 3 — False Positive Checklist

**Before escalating any case, every investigator must complete the FP checklist.
No adverse action without a completed, documented FP assessment.**

Work through each item and document your assessment (Cleared / Inconclusive / Confirmed Risk).

### GPS and location signals
- [ ] Could GPS anomaly be explained by known dead zones, tunnels, or rural infrastructure?
- [ ] Is there a customer delivery confirmation that corroborates the contractor's claimed arrival?
- [ ] Is the geofence miss pattern isolated or clustered? (Isolated = possible FP; clustered = risk)
- [ ] Is this the driver's first anomaly or part of a recurring pattern?

### Device signals
- [ ] Could emulator or root flag be explained by a legitimate developer or tester account?
- [ ] Is there a registered test device on file for this driver?
- [ ] Is the device shared with a family member in a legitimately shared household?

### Offer and incentive signals
- [ ] Is the driver a known power user with documented fast historical acceptance rates?
- [ ] Could incentive concentration be explained by legitimate high-availability behavior?
- [ ] Is the acceptance latency pattern recent (new behavior) or historical (established pattern)?

### Payout signals
- [ ] Is there a legitimate explanation for the payout account change (bank change, new account)?
- [ ] Has the driver previously verified a payout change through normal channels?
- [ ] Is the new payout account associated with a known suspicious instrument?

### Ring signals
- [ ] Could shared device be explained by a legitimate household or employer-provided device?
- [ ] Could shared IP be explained by carrier NAT or shared WiFi (low-risk scenarios)?
- [ ] Is there a second independent shared identifier beyond IP?

**FP threshold:**
- If 3 or more items are "Cleared" with no "Confirmed Risk": document as likely FP, downgrade confidence, recommend monitor-only.
- If any "Confirmed Risk" item is present with two or more corroborating signals: proceed to recommendation.

## Step 4 — OSINT Enrichment

OSINT enrichment is required for all CRITICAL and CRITICAL+ cases before action.

### 4.1 Identity document verification
- Check identity document authenticity signals.
- Flag: Are documents consistent with driver's stated identity and account history?
- Conceptual equivalent: identity verification vendor (e.g., Persona, Onfido, Socure).

### 4.2 Device intelligence enrichment
- Review device risk signals: known bad device fingerprints, device farm indicators.
- Cross-reference device ID against known fraud infrastructure.
- Conceptual equivalent: device intelligence vendor (e.g., Incognia, SEON).

### 4.3 Address verification
- Check delivery and registration address types: residential, commercial, mail drop, vacant.
- Flag: Are addresses consistent with a legitimate contractor's operating area?
- Conceptual equivalent: address verification service (e.g., USPS CASS, LexisNexis).

### 4.4 Account resale detection
- Check for signals that the account may have been sold or transferred.
- Common indicators: login location shift, device change, payout change in sequence.
- Conceptual equivalent: account resale marketplace monitoring.

### 4.5 Contractor presence check
- Verify business registry / contractor presence for accounts with commercial-scale activity.
- Flag accounts operating at scale inconsistent with a solo independent contractor.

Document all OSINT enrichment outputs in the case file. Note data sources and timestamps.

## Step 5 — Graph Analysis

For all cases with a ring flag or shared identifier signal:

- [ ] Review the NetworkX ring visualization attached to the case file.
- [ ] Identify all accounts in the connected component.
- [ ] Confirm shared identifier type: device, payout, IP, or campaign timing.
- [ ] Check whether any ring members have prior investigation history.
- [ ] Assess ring size: ≥ 5 members triggers mandatory escalation to Fraud Ops Lead.
- [ ] Note whether the ring is active (recent shared activity) or dormant (historical links only).

For rings with confirmed shared device + payout:
- Apply ring member flag to all accounts.
- Ensure all members are included in the case scope before action.

## Step 6 — Recommendation

Based on evidence review, FP checklist, OSINT, and graph analysis, select one of the following recommendations.

| Recommendation | When to Use | Required Evidence |
|---------------|-------------|-------------------|
| **Monitor** | Signals fired but no corroboration; FP checklist mostly cleared | Single signal, isolated event |
| **Continued investigation** | Evidence ambiguous; additional data needed | FP checklist inconclusive; OSINT incomplete |
| **Temporary restriction** | Strong multi-signal evidence; FP checklist shows no clear FP path | Two or more corroborating signals; OSINT confirms; analyst sign-off |
| **Escalate to Legal** | Ring ≥ 5 accounts; organized crime indicators; ATO with external harm | Fatal-tier evidence; four-eyes review complete |
| **Close as FP** | FP checklist cleared; no corroborating evidence | Documented FP assessment |

### Documenting your recommendation
- State your recommendation clearly.
- List the evidence items that drove your decision (by signal ID and signal name).
- Note any FP items you considered and why they were cleared or confirmed.
- Record analyst ID and timestamp.
- If recommending restriction: confirm contractor notification has been sent.

## Step 7 — Escalation Decision Tree

```
Is this a Fatal-tier signal?
  YES → Immediate escalation to Fraud Ops Lead.
        Notify Legal if ring ≥ 5 or ATO with external harm.
  NO  ↓

Is the ring size ≥ 5 accounts?
  YES → Escalate to Fraud Ops Lead regardless of individual score.
  NO  ↓

Is evidence for restriction met but FP checklist inconclusive?
  YES → Second analyst review before action.
  NO  ↓

Is analyst confident in recommendation?
  YES → Proceed to closure.
  NO  → Request senior analyst review.
```

## Step 8 — Case Closure

Every case must be formally closed with the following documentation complete:

- [ ] Recommendation documented with evidence citations.
- [ ] FP checklist completed and filed with case.
- [ ] OSINT enrichment package attached.
- [ ] Graph analysis screenshot or summary attached (if applicable).
- [ ] Analyst sign-off recorded (ID + timestamp).
- [ ] Contractor notification sent (if action taken).
- [ ] Case file SHA-256 hash verified at closure.
- [ ] Case status updated in queue management system.

For cases closed as FP:
- [ ] Signal(s) that fired are flagged for QA review.
- [ ] Brief note on FP root cause added to case file.
- [ ] If this is the third FP on the same signal in one week: alert Data Science for threshold review.

## Common Investigator Mistakes to Avoid

- **Do not escalate on a single signal without corroboration.** One GPS anomaly is not fraud.
- **Do not skip the FP checklist.** It exists to protect legitimate contractors and the company.
- **Do not use IP signal alone.** Carrier NAT creates legitimate shared IPs at scale.
- **Do not take action without analyst sign-off on Critical and Fatal cases.** No exceptions.
- **Do not assume ring membership = guilt.** A driver can share a household device without knowledge of fraud.
- **Do not close cases without complete documentation.** Undocumented decisions cannot be defended.
